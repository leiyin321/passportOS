ESP32-C3/8MB, no PSRAM, official BSP unchanged, LVGL9.5.0 native decoders.
Tests run 2026-10-25. Earlier measurements below precede the final sequential-file-reader optimization;
final regression results are recorded separately rather than silently replacing those measurements.

The initial render stress attempt timed out with approximately 2.2s launches. Sequential signed-package
reading and lazy per-image validation reduced launch time to approximately 210ms, after which the full
500-render run passed. First recovery test exposed an upload acknowledgement race; cleanup now precedes
the final install response and the complete recovery suite passed on rerun.

Logs are private: `local/hardware-render.log`, `local/recovery-result.txt`, and
`local/render-initial-result.txt`. Source tests live in `tests/assets/`.
A 48x48 I4 image uses 1,240 bytes including palette/header, versus 4,632 bytes RGB565: 73.23% less.
Thirty such assets use 37,200 bytes; current signed grid fixture is 44,315 bytes.
The final clean application is 1,767,840 bytes; pre-assets baseline was 1,753,920 bytes,
so the complete subsequent firmware change adds 13,920 bytes (not an isolated registry-only measurement).

Application visual/play QA and browser visual QA and interrupted physical power during
Flash programming are unverified. OTA accept/reject/pending-reset rollback was tested separately;
unattended network OTA has no exposed update entry point.
